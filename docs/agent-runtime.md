# AIFun Agent 运行时 v1

本次改造仅修改 AIFun，保留实施前的未提交工作。基线副本位于 `build/agent-baseline-20261003-165241/`。没有修改 TLM 源码、公共 `ITool` 接口或现有聊天记忆格式，也没有引入外部 Agent 框架。

设计参考固定为 [Codex b741e480 的调度](https://github.com/openai/codex/blob/b741e480e203f037ca726bc2a76d99a8e8668e66/codex-rs/core/src/tools/parallel.rs)、[历史预算](https://github.com/openai/codex/blob/b741e480e203f037ca726bc2a76d99a8e8668e66/codex-rs/core/src/context_manager/history.rs)，以及 DSH `dd6322d604e00eec1ba5e0c8541159906a21094a` 的有界工具批次、按序提交和保留工具配对的压缩机制。

## 开关与使用

COMMON 配置 `[agentRuntimeV1]` 包含 `enabled=false`、`diagnostics=false`、`taskAnnouncements="brief"` 和 `decisionModel=""`。`taskAnnouncements` 控制任务队列排队回执、完成通知和失败暂停通知对主人的外播：`detailed` 保留旧版确定性完整回执与通知；`brief`（默认）把排队回执交给前台模型，由模型按真实状态和自身人设自由说一句自然的话（空闲开干、手头忙、暂停、改细节、继续等状态各有不同说法，详见文末「任务外播：状态化回应与失败原因」）；`silent` 不发送任务通知，模型仍会对主人的直接指令自然回应。无论选择哪种模式，完整事实都写入服务端日志；主人明确询问失败原因时始终返回运行时记录的原因，不受该模式影响。运行时保持实验性、默认关闭：跨版本正确性回归与单项性能测试不能替代原计划要求的旧版/新版整体耗时验收。

独立决策服务的 `enabled=true` 不会自动打开主运行时；复测决策路由需同时开启 `[agentRuntimeV1].enabled`，测量阶段再开启 `diagnostics`。2026-10-11 本地放箱日志仍走主运行时关闭的普通聊天路径，六轮 DeepSeek 往返约 9.60 秒、指令到回复约 10.16 秒，不能作为决策路由的验收数据。此次已打开开发环境 `run/config/touhou-aifun.toml` 的主运行时和诊断，保留现有 Perplexity 决策配置；发行默认值仍保持关闭。

普通聊天兼容路径的 GUI 工具定义现在按 callback 区分：仅后台 `TaskCallback` 暴露 `complete_task` 及完整合同说明；普通聊天和基模客户端只提供 `close_after`，执行层仍拒绝越界完成声明。普通聊天实际成功开箱后，下一请求自动提供已触发的检查、动作、批量、等待和关箱工具，复用冻结目录及实际 schema 预算；开箱失败不加载。无需再单独调用 `load_tool_schema(gui_batch)`。普通聊天的最终自然语言回复仍由聊天模型生成，后台任务则继续核验实际完成条件后直接收尾。

该兼容修正通过 360 项 JUnit，以及 Forge 47.2.0 / 47.4.20 独立平坦测试世界各 78 项服务器 GameTest；新增场景实际转移五组各 64 个物品并同次关箱，覆盖开箱失败不加载、冻结目录复用、两种协议的完成参数隔离，以及越界声明不能移动物品。普通地形测试世界中的旧四箱场景出现寻路失败，最终验收使用独立平坦世界。上述为本地回归，不代表真实 DeepSeek／Decider API 的耗时测量。

开启后，每位女仆最多同时执行一个行动任务，另外容纳四个排队任务。正常聊天和问进度独立执行；新行动要求默认排队，明确“改做……”才替换，补充条件在行动边界生效。含糊要求由前台模型澄清。明确停止和停止按钮直接取消当前任务并暂停队列，清空队列需要明确请求。控制入口验证实际主人权限。

退出、主人离线、女仆卸载和关闭配置会暂停并保存检查点。重新进入后等待主人要求继续，先观察现场，再执行动作。**只有队列里确实存在未完成任务时才会保持暂停；空队列不会因为上一局结束或世界重载而带着 `paused=true` 恢复**，否则每条新指令都要先说一次“继续”。不会恢复旧 GUI、旧 future、旧帧或旧观察作为动作凭据。GUI 操作预览显示当前任务、队列及暂停/继续/取消状态。

仅 AIFun 的 Chat Completions、Responses、ChatGPT 订阅、Anthropic 客户端接入新运行时；原版 TLM 客户端保留兼容路径。网络协议版本为 17，服务端与客户端需使用相同版本的 AIFun。

### 独立决策服务：JEV / Perplexity Decider

设置入口为 AI 设置 → **后台执行模型** → **独立决策服务**。原有 `decisionModel` 键仍表示后台执行 LLM，继续负责完整规划、自由文本和回退；已有选项无需迁移。新服务使用原生概率决策协议，不加入普通聊天站点，不生成聊天、SSE 或 TTS，也不改变首次前台意图判断。

| 服务商 | 默认完整接口 | 默认模型 |
| --- | --- | --- |
| JEV / TypeSafe | `https://api.typesafe.ai/v1/systemone` | `jev-1.13.0` |
| Perplexity | `https://api.perplexity.ai/v1/decisions` | `pplx-decider-v1.1-27b` |

COMMON `[agentRuntimeV1.decisionService]` 默认 `enabled=false`、`provider="jev"`、`timeoutMs=3000`、`minConfidence=0.9`。各服务商的 `.jev` / `.perplexity` 子节分别保存 `endpoint`、`model`、`apiKey`，切换服务商不会覆盖另一家的凭据；修改在新执行代际生效。游戏界面复用站点编辑权限，服务端只回传 Key 是否已配置。空 Key 保留原凭据，清除必须点“清除 Key”；启用前必须有 Key。接口 URL 为完整路径，不自动拼接聊天后缀或尾斜杠。Key 保存在服务端 COMMON 配置中。

后台先用代码派发本代必需的首次现场扫描，默认直接由执行 LLM 操作，不串行等待模板／技能探测。只有显式开启 `startupTemplates=true` 才尝试有限常见模板。默认工具定义不携带结构化步骤的大量可选参数；确有重复／分支工作需要时，用 `load_tool_schema(tool_name="group:task_actions")` 加载。`update_task_plan.action_steps` 可只描述下一段有用的执行步骤，完成条件仍须覆盖全部主人要求，必须单独调用登记；不能在同批登记后再派发重复动作。每步含 `description`、`alternatives`（`tool`、`arguments_json`、`when`），以及可选服务器谓词 `precondition` / `until` / `skip_if`。`arguments_json` 是固定参数 JSON 对象字符串；一个完全确定的动作由代码直接执行，多个动作或未填的枚举／布尔参数编译成同一次 Choice／Noul 请求。Score 协议已解析并验证，当前动作路由不使用评分来代替完成证据。传统文本计划继续由执行 LLM 执行。

模板可用 `$live.session_id`、`$live.revision` 绑定当前 GUI。对于当前完成阶段的第 N 个原子完成条件（0 起），`$live.remaining_N`、`$live.from_slot_N`、`$live.to_slot_N`、`$live.transfer_count_N` 由真实净转移、当前容器和合法库存槽位计算。重复搬运使用 `until` 核验实际数量，代码限制自动派发的转移不超过对应合同剩余量，批量参数还核对累计量。旧槽位、旧 session 和视觉坐标不能作为新动作依据。

候选只来自当前符合触发条件的冻结工具目录，并由本步骤的明确意图裁剪；无需额外 `load_tool_schema` 模型轮次。普通枚举／布尔字段自动生成问题，必需自由文本由执行 LLM 先提供；缺少开放参数、绑定不可用、图片解读或未知协议返回执行 LLM。所有后台工具均可进入这个判断流程，不能闭合参数的工具保留执行 LLM 路径。首版视觉动作继续走已有视觉链路，未把 Perplexity 图片能力接入 GUI 自动点击。

Choice 使用返回的 `confidence`（不等同于最大概率），Noul 默认 ≥0.9 为真、≤0.1 为假，中间值回退。每次最多 128 个问题、每个 Choice 最多 255 个候选，操作输入预算 8192 估算 token；超限整体回退，不丢掉必需问题或拼接生成自由文本。所有女仆共享本服务进程的 10 请求／秒门控，超限直接回退。HTTP 超时、429／服务错误、无候选、低置信度和无效结果不在决策路径排队重试；认证／协议错误停用本代的远程判断。不会自动从 JEV 切换付费调用另一家。

决策服务持有原始 HTTP future，可随任务取消；超时先取消传输，再交回执行 LLM。响应回到服务器线程后重新检查代际、目标版本、主人和判断所依赖的现场：模板判断保留目标身份／标签，数量分配保留选中来源的已观察库存，放物还保留女仆库存；无关箱子的库存变化不再使判断失效。动作判断仍检查当前 GUI、位置、库存和固定动作目标，派发时照常执行完整现场校验。模型输入合并具有相同权限的空槽并保留槽位映射，不重复发送旧菜单；服务器私有容器库存和完整方块 NBT 不作为模型观察。无法表示的动作分支保留其选择含义，选中时回到执行 LLM。选定动作仍经过同一工具 codec、现场权限／槽位校验、有序结算、进度保护和档案记录。卸载／重启可能先保存物品修改、后保存步骤推进，因此恢复时保留实际事实并重新规划模板，避免重放一次性动作。

完成条件新增 `maid_state`（`state=follow/sit/schedule/work_task`、字符串 `value`）和 `eat_food`（`food`、实际 `count` 份数、可选 `finished` / `position`）；食用事实在每次真正消耗的服务器边界登记，取消后仍可恢复已吃掉的份数。`finished` 还核对现场，不能拿旧完成记录代表同位置新放的食物已经吃完。所有结构化步骤、完整完成合同和 GUI 收尾都满足后可直接结束任务；高置信度或模型“成功”句子不能替代事实核验。

诊断新增 `decision_request:jev/perplexity`、`decision_fallback:*` 和 `decision_dispatch:deterministic_*`；`scripts/agent-trace-report.py` 分开统计决策请求次数／占用时间、执行 LLM 耗时、直接步骤和回退原因，重叠跨度不累加成任务墙钟。原始使用量、请求／返回模型名和请求 ID 留在任务档案的决策元数据中；日志不输出 Key、对话或图片。前台聊天导致的完成通知等待仍单独统计。

协议依据：[JEV 官方接口](https://docs.typesafe.ai/api)、[Perplexity Decisions API](https://docs.perplexity.ai/docs/decisions/quickstart)。本地兼容回归使用模拟 HTTP；没有实际决策服务凭据时，不把模拟耗时宣称为真实模型提速。

### 常见模板、目标绑定与失败恢复

独立服务启用、凭据可用且显式配置 `startupTemplates=true` 时，首次扫描后合并一次启动判断：模板选择、目标范围，以及预算内可提前确定的物品／字面数量和技能目录选择。模板包含跟随、坐下／起立、工作时间、工作模式、从容器取物和向容器放物六类，也提供有序的两段组合：一个受支持动作之后设置一种不同的最终女仆状态，例如取物后坐下、送物后跟随。完整合同同时包含转移数量和所有选定最终状态；切换工作模式不代表已完成种田、战斗等工作。不支持任意长组合、取物后放物或仅描述中间状态的目标。完整覆盖判断或任一适用答案不确定时回到执行 LLM；新工作、模糊数量和无法辨别的目标组保留完整规划路径。一次回退后，本代不会反复启动同一模板判断。已有完整合同可重建受支持的转移／状态步骤，原合同逐项保留。

明确命名物品且给定每个来源的字面数量时，可先绑定物品／数量并直接登记完整合同，省去预先巡检；物品名来自实际注册 ID、本地名称和有限别名，不代表已经观察到箱内供货。单一来源的明确总量也可走此路径。放物数量基于当前真实背包，不凭模型猜库存。取全部、不明物品、多来源总量分配，以及来源侧“组”单位的实际堆叠限制仍须只读检查选中的容器，确认完整菜单覆盖与当前数量一致。已绑定的字面数量可在巡检后复用，省去第二次数量判断。每种物品最多 8 个字面数量，物品候选最多 16 类，容器最多 8 个；条件和步骤仍受原上限约束。数量不是自由生成值；“两组鸡蛋”按实际物品堆叠上限 16 得到 32，存在同 ID 不同堆叠限制时不猜测。全部取物使用实际观察数量；不足库存、无法表达或多目标分配不成立时回退，不能扩大目标组凑数。

同一连续转移阶段内，相同容器的多个物品共用一次打开／关闭；独立转移条件及其原始索引保留，不能跨过状态步骤改变执行顺序。每次实际搬运重新计算当前合法槽位和剩余量，不预存批量槽位。巡检按执行首箱放在最后的顺序进行，若最后菜单仍属于当前任务、目标一致且通过有效性、距离和活动范围检查，可直接复用。开箱用 `skip_if` 跳过已完成转移的准备，实际搬运用 `until` 和当前 `$live` 剩余数量绑定。

复杂计划可加 `target_binding={kind:block|container|entity,description:...,scope:...}`，在参数中用 `$target.x/y/z/registry_id/entity_id/entity_uuid`。候选只来自实际扫描记录，方块坐标按扫描时原点换算；告示牌须实际附着到目标且文字未变化。可选非空 `scope` 最长 64 字符，标识一个子任务；相同作用域和查询可复用已选定目标，但每次仍核对当前坐标、维度、注册 ID、实体 UUID 和标签。自己搬动物品造成库存变化不使语义绑定失效，目标／标签变化则重新决策；独立子任务必须使用不同作用域。未声明作用域仍逐步判断。绑定仅存于执行代际内，补充目标、取消／重新执行和回退会失效。运行时还核对加载状态、活动范围、实体存活并在派发时验证实际动作。内部容器库存证明不送给模型。首次选择的单一候选仍需语义范围判断，不能仅凭附近只有一个目标就派发。

已有完整转移／女仆状态合同收到明确补充时，有限修订可修改已有数量、换成已观察目标或修改已有最终状态。修订以最新主人原文和上版完整合同为依据，不受影响的条件保持不变，已结算转移继续计数。已从旧箱取到 2 个、要求总共 5 个并换来源时，保留旧箱 2 个事实，仅从新箱补 3 个。数量低于已结算值、不明多来源分配、新物品／工作、增加或删除目标等回到执行 LLM；无实际合同变化也回退，不能把旧任务完成冒充补充要求已落实。修订基线随检查点保存，连续未解析修订不使用过时基线。

失败恢复优先由代码处理已知过期菜单、丢失会话与失效现场：重新检查、重开同一授权目标或重新扫描。有多种合理恢复方式时，仅让决策服务选重新检查／重开／观察／暂停／交回执行 LLM；不提供盲目重试修改物品选项。每步最多两次恢复，只重建当前合法绑定和实际剩余量。已结算转移不清零，不重复搬运；交易、吃东西、持物交互等无法证明幂等的一次性动作仍回到执行 LLM。所有动作保留原 codec、现场校验、权限和完成核验。

服务器 QA 可用 `-PguiQa -PfourChestQa -PisolatedAgentQa -PagentQaRunId=<简单名称>` 创建独立 `build/agent-qa-<名称>` 测试目录，避免重复测试积累的档案容量干扰；不清理玩家世界或旧测试记录。

### 合并启动判断与真实技能目录选择

`StartupItemBatch` 在首次模板／目标请求中附加互不重名的 `receive_*` / `deliver_*` 问题，只消费最终选中分支的答案。取物候选来自明确命名的注册物品，放物候选和单位来自真实背包；尚未观察的来源数量明确标为未知。模板完整覆盖判断与每个分支的转移覆盖判断独立保存，不相互覆盖。明确数量可一次判断后直接执行；“全部金锭”和多来源总量可复用启动答案，但仍须打开菜单核对库存并分配数量。来源侧“组”单位、未知物品等仍保留观察后绑定；合并超过问题／候选／8192 token 预算时保留完整原问题并走原分阶段路径。适用数量低置信度先回退；不适用分支的低置信度不阻止纯状态模板。合并放物判断会额外核对真实背包是否在响应期间变化。

`DecisionSkillCatalog` 只从当前实际 `SkillLoader` 注册表与已通过 trigger 的 `use_skill.name` 枚举交集读取名字和完整描述。基模本来已经提供技能名枚举，这次补的是启动时主动选择技能，以及结构化动作选择中的描述上下文。有限候选使用独立编号和明确 `none`，不合成技能名，不根据关键词强行选技能。首次模板回答必须明确选择完整规划 `llm`，且技能选择达到置信度，才通过现有 codec／异步工具路径调用一次 `use_skill`。完整模板可直接执行时忽略技能答案。读取后将原始指导内容交给执行 LLM 规划复杂任务；读取技能本身不登记虚假完成合同，不执行正文指令，也不宣告工作完成。知识类型继续复用已有短文本直返／长文摘要缓存和本地语言引用路径。目录为空、候选／输入超限、低置信度或 `none` 都保留正常规划，不截断技能候选凑预算。

技能目录私有指纹包含正文、元数据和引用的内容哈希，决策模型仅看到实际名字／描述／类型。目录热更新会使尚未接受的选择失效；取消和新代际仍由原任务门控处理。新诊断 `decision_startup_merged` / `decision_skill_selected` 与原 `decision_response` 共同记录合并请求和选择位置；使用现有 Trace 报表统计实际请求次数，不能把物理等待或摘要时间算成决策速度。

2026-10-11 本轮验证：360 项 JUnit、6 项 Python 报表测试通过，Forge 47.2.0 / 47.4.20 各 76 项必需 GameTest 通过；串行决策场景扩展为 44 个。启动合并的场景 2/3/18/24/25 同时断言零巡检、一次原生 HTTP、真实数量和完整最终状态；19 的“全部金锭”与 43 的多来源总量都保留库存巡检，但只需一次原生 HTTP，复用末箱菜单和启动数量答案。17 的两组鸡蛋继续使用真实堆叠上限。38 在等待响应时修改背包，确认没有开箱或转移；39 的不适用数量答案不确定仍正确跟随；41 的适用数量低置信度在任何开箱前回退。单元测试另覆盖合并预算超限和覆盖问题互不覆盖。

技能场景 31/32 分别走 Perplexity/JEV 原生接口，实际加载一次 `use_skill`，第一次执行 LLM 收到原始正文，完成合同仍为空且任务未完成；42 验证知识类型的实际正文和本地语言引用。33/34 的低置信度／none、35 的请求期间正文热更新、36 的取消、40 的超预算完整目录都不会读取技能或修改世界；37 验证结构化动作通过真实技能名枚举及描述选择并读取技能，然后实际跟随完成。日志为 `build/decision-start-skill-server-47200.log`、`build/decision-start-skill-server-47420.log`，普通发布构建使用 `build/decision-start-skill-release.log`。原生 HTTP 采用本地模拟，不宣称真实模型延迟或整体提速百分比；未修改玩家配置／世界／旧队列或首次前台意图判断。

后续仍可研究长知识结果中与任务有关的原文段落选择。`KnowledgeSummaryCache` 已对短文本直接返回、对同源同查询缓存结果；段落筛选需要保留完整步骤、数量、条件和来源，不能用相关性答案冒充事实摘要。长文摘要和 `MemoryExtractionCallback` 的新事实文本仍需生成式 LLM。确定步骤每次仍经过 `TaskCallback.next` 重建检查点和工具快照，可另行测量并优化这部分代码成本；既有世界动作结算顺序必须保留。任务完成核验、权限、菜单槽位、缓存命中与本地记忆检索已有代码事实路径，不新增决策请求。

## 任务、事实和记录

`AgentExecution` 明确区分聊天、任务、知识提取、设置生成和辅助请求，并携带女仆、聊天轮次、任务及代际。任务使用独立 `TaskCallback`、消息历史和操作集合，前台聊天换轮不会丢弃后台结果。知识摘要子请求继承父执行的取消条件。

`AgentTaskState` 保存目标、约束版本、计划、当前步骤、阶段、证据引用、失败、Schema 加载集合和完成条件。状态包括 queued/running/waiting/paused/completed/failed/cancelled。`update_task_plan` 维护步骤；模型不能通过改计划覆盖真实执行事实。

独立的版本化女仆 NBT 保存任务与队列。世界 SavedData `touhou_aifun_agent_archive_v1.dat` 保存有界完整记录和原始结果，采用字节数组避免 NBT 字符串长度限制。记录包括模型步骤、调用、结果、取消和真实物品转移。归档有容量限制，活动记录无法继续保存时安全暂停。原始结果淘汰后保留摘要并明确报告引用失效，不重新执行原操作。

**执行器中间正文可查（2026-10-19）**：后台执行器每轮 assistant 正文（工具调用同轮的 content + 收尾正文）写入该任务档案的 `narration`（最多 24 条、每条 ≤1000 字；附加字段，旧档案缺省为空），同时每轮留一条 `assistant_text` 记录（全文存 result ref，摘要 ≤200 字）以便超出窗口后仍可追溯。执行器系统提示 `AgentTaskInstructions.NARRATION_POLICY` 要求**每轮响应先写 1–3 句事实性执行情况**（含上一批工具结果的真实数量/物品/位置/失败摘要），最终回复必须是事实性执行报告；某轮只有工具调用而没有正文时，下一轮 checkpoint 会带 `intermediate_narration_required` 提醒并记 `narration_missing` 诊断（缺正文不会暂停任务）。前台主模型有两条查看通道：① 每次前台请求注入的 `## Runtime task status for foreground` 携带最近 2 条正文（`ForegroundTaskStatus.narration`，每条 ≤200 字）；② 按需调用 `read_task_result(result_ref="task_narration")`，从最新往回分页（`offset`/`next_offset`，单次 ≤8 条、≤4000 字），带 `task_id` 可读已离开队列的归档任务，仅实际主人可读；更早的单轮正文用 `task_trace` 记录里的 result ref 再读。执行器正文仍然不画气泡、不朗读、不写入聊天历史或长期记忆：它只是可检查，不会被重新播放。

GUI 原子动作首先登记真实净转移，再提交模型结果。游标拾取不等于收货，实际落入女仆库存才登记；返还来源不重复计数，反向转移抵扣。GUI 关闭或卸载时的迟到游标结算进入世界归档，恢复时按事实版本与较旧实体检查点核对，避免重复搬运。

完成验证支持 transfer、inventory、position，以及最多 16 项原子条件的 all 组合。转移条件核对物品、维度、容器位置、方向和真实累计净数量；库存、位置条件读取当前服务器状态。补充数量后重新计算条件，现场未重新观察、条件缺失或未满足时不能凭模型文本标记成功。模型过早宣称完成时允许一次基于真实证据的纠正规划，仍不满足则暂停；不会自动重放世界修改。尚无领域验证器的开放任务保守暂停。

## 上下文与 Schema

完整归档与模型上下文分开。每轮提供当前用户约束、任务检查点、完成条件、相关事实、近期步骤及已加载工具。约 80% 消息预算触发精简，目标约 60%。先删除同一已结束批次的重复 GUI 快照，再按调用/结果完整组压缩。保留原始坐标、物品数量、真实动作、错误和未完成事项，保留未结束调用、最新批次和用户约束。

确定性精简仍无法容纳的旧自由文本才使用模型摘要，子请求可取消且不加载行动工具。精简后仍超预算会暂停，不发送明显超预算的请求。完整 GUI 首次结构留在当前工具结果，不再把同一套槽位重复塞入检查点。

`read_task_result` 按引用分页，每次含头部约 2,048 token；引用有上下文随机前缀，持久化后仍指向原结果。缓存同时有字符数、条目数及归档上限。

`load_tool_schema` 保留原入口，支持 `group:gui` 等工具组。后台世界／GUI Schema 按阶段提供，普通流程自动加载；其他明确加载的 Schema 在任务内保留，目录区分当前直接可用／可发现工具，短目录与完整说明分开。注册表、技能定义和 `ToolSchemaDependencies` 声明的动态依赖变更会失效，执行前再次核对可用性。第三方可通过 AIFun 依赖声明接口提供版本，不需要改 TLM。

## 调度、扫描和工具成本

工具元数据描述线程、资源、并发、取消、结果预算和缓存。默认独占；已适配且独立的网络工具最多两个并行。GUI、背包、移动和未知第三方工具保持串行，世界访问仍在服务器 tick。每批最多 16 次调用，独立结果缓冲按调用顺序提交；取消后停止派发，已接受调用保留对应结果或取消记录。

操作集合覆盖原始模型 HTTP future、扫描、GUI、视觉和摘要。动作边界核对任务代际、目标版本和观察状态，状态不确定的世界修改不盲目重试。无进展检测结合库存、净转移、位置、阶段和有界状态历史，覆盖交替循环；两次提示重规划，继续无进展则暂停。

扫描支持 `intent=overview/locate/read_signs/inspect_area` 和 `detail=summary/full`。overview/locate 保存全景实际命中的通用方块，read_signs 走告示牌候选快路径；指定小范围时 inspect_area 逐格检查，独立于重点标签。`observed_blocks` 通过 `observation_id/next_offset` 分页，任务上下文压缩也保留该页与续读字段。多女仆共享每 tick 有界工作量，轮转调度，卸载及时取消。详见 [小范围精查](multimodal-observations.md#通用方块扫描与小范围精查)。

缓存将几何观察与 focus 排序投影分离，检查姿态、开始/完成观察年龄、区块加载状态和区域版本。服务器方块更新使涉及区域失效，旧观察不会通过重置完成时间续期；告示牌读取重新获取文字。摘要返回重要目标坐标和未覆盖/省略说明，截断不能证明目标不存在。截图并行、主模型图片和回看能力保留。

容器发现优先已知目标及方块实体候选，非方块实体菜单保留有界回退搜索；候选接近位置用于导航，减少重复 BFS。支持明确的 `registry_id@x,y,z` 目标，仍检查坐标空间、冲突参数和实际方块类型。

GUI 首次返回完整槽位结构，后续默认只返回变化槽位、游标、数量和状态版本，关闭返回收尾结果。槽位说明区分主手、副手、背包，并给出背包索引。`gui_batch` 最多 16 个有序语义动作，每步校验，失败即停并报告部分成功，不提供事务回滚。兼容既有工具和无歧义的 `from_slot` 参数；冲突、非整数槽位、过期观察仍拒绝。未知协议和视觉动作不能绕过适配器、帧与布局校验。

知识/Wiki 约 2,048 token 内直接返回相关原文，较长资料才摘要；缓存按来源、内容、查询、语言、站点和模型区分。网页默认返回相关段落、必要链接和完整抓取引用。`query_game_context` 分类别计时和版本复用，位置及库存不长期缓存。

诊断只记录阶段、耗时、状态和体积，默认关闭；任务路径不输出含完整对话的请求 DEBUG 日志。阶段覆盖模型等待、排队、工具执行、导航、客户端回传、视觉和检查点。重叠阶段不能相加作为任务总耗时。

## 分类完成条件与中途补充修补（2026-10-04）

`AgentCompletionRules` 在登记搬运完成条件时检查最终保留数量与当前、已记录及计划中的供给。如果唯一的一把铁锹既要求转出又要求最终留在背包，登记即失败并返回具体冲突，不先执行转移。库存足够保留一把，或计划从其他来源接收另一把时仍可成立；相同目标的重复谓词取最大要求，不能把一个容器的同一物品净转移同时要求为正向和反向。Schema 明确 `inventory` 是最终背包下限，不是初始库存或前置条件。

完成检查点及申报失败结果提供每个未满足谓词的物品、要求数量、实际数量、剩余数量和位置/距离；模型无需再通过成功句子或反复开箱猜测阻塞。历史任务的错误完成条件不会被模型静默删除：新的现场观察发现供给冲突会暂停，保留真实转移记录，等待主人明确补充最终要求。给玩家的暂停说明使用简短的物品数量说明，不直接展示内部诊断 JSON。

## 2026-10-05 请求前缀与 token 缓存治理

发现 Anthropic 适配器会把所有 SYSTEM 消息提升到顶层 system，包括逐轮变化的任务检查点、game_tick、完成数量、现场证据和前台任务状态。它们位于工具历史之前，改变进度会改变整段历史共同前缀。DeepSeek 的缓存依赖已经落盘的匹配前缀，默认开启；Anthropic 兼容接口忽略 cache_control，所以没有增加一个无效的缓存开关。依据：[DeepSeek 缓存规则](https://api-docs.deepseek.com/guides/kv_cache/)、[Anthropic 兼容详情](https://api-docs.deepseek.com/guides/anthropic_api/)。

受管理的 Anthropic 请求只把开头的稳定系统规则放在顶层 system；后续运行时消息、当前检查点、已加载工具列表和情绪提醒放到全部 tool_result 之后的运行时上下文。固定系统规则说明这些状态和必要步骤的含义，观察依然是数据。所有工具结果仍有原 call id，并保持成组、按序提交。旧检查点继续被替换，不积累重复状态。辅助知识提取和设置生成维持原系统消息兼容路径。实际动作权限、现场验证和任务完成检查均未放宽。

把容器范围、完成条件和最终 GUI 操作指导移到任务创建时的一次性固定系统规则，检查点只重复简短下一步提醒。工具目录与可选 Schema 按工具 id 排序，已加载列表排序；实际增加工具或动态定义变化仍会正常改变请求，不为了缓存维持失效定义。OpenAI Chat Completions、Responses 和 ChatGPT 订阅原先已经保持系统消息的序列位置，这次共用稳定规则和工具排序。

## 2026-10-11：后台工具按阶段裁剪

`TaskToolSelection` 根据当前执行代际的新观察、完成条件、实时条件核验和 GUI 是否打开，在服务器线程准备每轮工具集合。工具注册表及第三方 Schema 仍按定义版本冻结复用；阶段切换不重建全部定义，不增加分类模型请求。所有协议适配器、工具目录和上下文预算使用同一集合。普通聊天的工具选择保持原逻辑。

| 后台阶段 | 常规完整 Schema 数量 | 用途 |
| --- | ---: | --- |
| 观察 | 4 | 环境扫描、游戏上下文、证据读取、按需加载 |
| 规划 | 6（GUI 关闭）／9（GUI 打开） | 容器观察、登记完整条件，以及按序开始操作 |

这是常规集合，不是固定硬上限；不可用工具仍过滤，失败时补回环境扫描与证据读取，明确加载的扩展工具可以增加数量。联网、时间、技能和女仆状态切换等原核心工具不再常驻后台完整 Schema，只在简短目录中保留发现入口，需要时按精确 id 加载。已加载的非阶段工具在任务内保留；GUI 整组加载的历史状态不再导致所有 GUI Schema 常驻。

白名单按当前执行代际、目标版本、计划文本与步骤编号生效，不持久化到任务事实。改变步骤或计划、主人补充、错误恢复、读档／新代际后恢复正常阶段菜单；`allowed_tools: []` 也可显式清除。未知名称或非法列表在修改计划、完成条件前整体拒绝。此功能只选择工具，不改变任务目标、约束、完成条件和已执行账本；模型无需为优化名单额外增加一轮请求。

生效时，实际发送的 Schema 是白名单、按需显式加载的工具和必要恢复工具的并集，再与当前注册／触发／现场权限相交。`update_task_plan`、`load_tool_schema`、`read_task_result` 保留；现场尚未重新观察时保留扫描入口。`load_tool_schema` 只扩展准确指定的能力，未加载的 GUI 工具不会因旧 group 状态一起恢复。目录、四种协议客户端与上下文预算统一读取这一选择结果，原有 475K 默认预算不变。

执行端为每个模型响应冻结实际公布的白名单。在同批修改计划或加载 Schema，只会影响下一次请求；本批未公布的模型工具调用返回 `tool_not_in_allowed_tools`，不开始动作，并进入正常恢复。白名单不是给本地执行器增加权限的机制：已验证的原生决策／菜单清理仍使用原有现场、完成条件、所有权和实际数量保护，不受 LLM 菜单误阻塞。

原生协议字段仅发送到 HTTPS、精确主机名 `api.openai.com` 的 OpenAI 官方端点，且只在当前任务启用白名单、有函数工具、没有既有 tool_choice 时添加。Chat Completions 使用 `tool_choice.allowed_tools` 嵌套结构；Responses 使用 `tool_choice.tools`／`mode`。DeepSeek、Anthropic、OpenCode Go、其他兼容服务与 ChatGPT 订阅后台都只接收已经裁剪的工具定义，不假定它们支持同一字段。

### 2026-10-18 自动选单与配方证据优化

后台输入预算继续为 **475000**。`allowed_tools` 提示改为覆盖“完成当前步骤”的工具，包括开菜单后的实际动作，避免取料步骤只选开箱／查看／关箱。白名单除了文字步骤和目标版本，也绑定服务器已验证的顺序阶段；实际阶段前进后自动恢复正常阶段菜单，模型忘记更新 `current_step` 不会使旧选单一直阻挡合成／交付。当前响应仍使用冻结的工具集合，阶段变化不放行同一响应中未公布的调用。

## 任务外播：状态化回应与失败原因（2026-10-18）

COMMON `[agentRuntimeV1].taskAnnouncements` 是新增的单一配置，控制任务队列三类外播：排队回执（接单／替换／追加／恢复／停止／暂停）、完成通知和失败暂停通知。

`brief`（默认）不再使用固定台词。运行时在回执中发布权威调度状态 `controlled_task_dispatch`：`starting_now`（空闲，马上开始）、`waiting`（手头还有未完成任务）、`paused`（队列暂停）、`amendment_next_boundary`（当前任务执行中修改细节，下个动作边界应用）、`amendment_pending`（暂停中修改，继续后应用）、`resuming`（继续此前任务）、`stopped`／`queue_paused`、`nothing_to_resume`。回执同时附带接受的目标、主人补充原文和当前在忙的目标；前台模型据此和女仆人设自行生成一句自然、短小的回应——空闲开干时说「好，我这就去」「好，开干」一类的话，手头忙时说「记下了，忙完就去」，中途改细节时说「了解，改成……是吧」。这些只是风格提示而非脚本，模型可以按心情复述大致内容；队列位置、队列数量等机械细节仍不进入聊天。

完成／失败通知在 `brief` 下也由一条**后台小请求**措辞：请求附带女仆角色设定摘录和有界的最近聊天摘录，让这句话像聊天续句而不是状态汇报；只收到完成／失败、接受的目标和等待任务数，不接收完成条件、技术错误或失败原因。聊天语言与 TTS 语言不同时，请求返回 `{"chat":...,"tts":...}` 两个字段，分别用于气泡与朗读；同语言时只有一句。输出被压成单行短句（最多 120 个码点），任务队列会等这条通知就绪后按序发送。

通知在显示气泡的同时通过女仆已配置的 TTS 站点朗读（受 `TTSEnabled`、站点启用状态、私密女仆主人有可用连接等条件限制；系统／本地 TTS 由 TLM 自己写入气泡，运行时不重复添加）。没有 TTS 或不可用时仍显示文字气泡；凭据缺失、站点不可用、请求失败、超时或答案不可用时回退到固定短句（“做完啦～”／“这个先卡住啦，等下再弄吧～”），并记录 `AIFun task announcement ... source=fallback`。失败原因仍只写日志，并在主人明确询问时由回复守卫明确告知。这条小请求不复用聊天流程、不写聊天历史、不参与 TTS 流式回复。

`detailed` 保留旧版确定性完整回执（目标、队列位置、等待数量和结果）与完整完成／失败通知，便于需要精确文本的部署；`silent` 不发送任务通知，排队回执同样交给模型自然回应，但禁止播报完成、失败、队列位置／数量或状态。

无论模式如何，完整事实都写入服务端日志：控制动作、女仆 UUID、任务 id、目标、状态、队列位置、队列是否暂停、推导出的 dispatch，以及完成／失败的成功标志、等待数量、完整结果；执行模型或档案不可用导致的暂停也记录原因。日志行分别以 `AIFun task control`、`AIFun task outcome`、`AIFun task paused` 开头，不进入聊天或 TTS。

主人明确询问失败原因时不受静音配置影响：前台回复守卫识别「为什么失败／卡住／暂停／没做完」等问法，在有暂停或失败任务时直接返回运行时记录的 `outcome`（含目标、暂停或失败状态、具体原因），内容过长时仍保留前 1024 字符；没有记录到具体原因时会说明可能是被暂停、重新载入或主人停止，而不是用模糊句子带过。普通聊天和与任务无关的问题不会被该守卫改写。

`taskAnnouncements` 默认 `brief`，普通聊天、语音、GUI 队列预览与 `task_control(action=status)` 均不受影响；后者仍可显式查询完整事实。部署后需要重启服务器加载新配置键，旧 `touhou-aifun.toml` 缺少该键时会自动写入默认值。
